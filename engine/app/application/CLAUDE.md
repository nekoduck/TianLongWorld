# application/
> L2 | 父级: engine/app/CLAUDE.md

应用层：用例编排。它把命令翻成领域调用、把获准之举的物理边界交给一席裁决（文本在胜负未定或挂着时钟时请地下城主推演、点选在胜负未定时交给气运）、把定案交给世界时钟算出这一招之后的心跳（余波 / 光阴 / 扩散 / 生态 / NPC 行军）、把相撞的中断交给 H-Agent 的判官并在规划时机请议程大模型（npc_agent）、把事件推给投影、先算可供性目录、退路菜单与方位导航，再把快照与目录交给大模型渲染（同一次调用里挑招配风味），
自身不含业务规则（规则与可裁区间在 domain/rules/、domain/combat.py、social.py、covert.py、stakes.py，世界物理在 domain/heartbeat.py，空间与迷雾在 domain/geography.py，NPC 的议程闸门、行军与相撞裁决在 domain/npc.py）。
对外边界是 bus.py：命令进、回合消息的异步流出；对内只依赖 domain 的端口与本层的 LLMClient 抽象。

INTENT_SYSTEM：LEARN 涵盖入门与精进、REST 调息疗伤独立成动作（练功疗伤以疗伤为准）、USE 服药敷药（服药疗伤以 USE 为准）、THINK 沉思（回想、盘算、权衡，不动手不开口不挪步）、七种手段与九种所图各一句判据（「用于 / 见于」由 approach 兼容表生成，表一改提示词跟着改）、topic 话题指称（说话的对象不进 topic）、motivation 此行所为（只在 MOVE 时写去找谁、去做什么，≤24 字，没说即空串、不替玩家编来由，别的动作一律空串）、撂话离场是 MOVE（话只化进笔墨），示例逐条带 motivation，含沉思与带所为的移动；场景词表的人物带称号与别名、已会武学带火候；LLMIntentParser 带场景词表与输入转义、结构化输出、重采样后兜底 INVALID、LLMError 透传（回合不写任何事件）；HeuristicIntentParser 离线动词 + 关键词 + 场景词表解析：手段按 借势 > 人情 > 武力 > 计谋 > 潜行 > 言辞 认关键词并经 _fit 按兼容表退回寻常（偷袭是出手不是潜行）、打探的话题取中心词且须经 rules.ground 落得了地（落不了地只是闲谈）、威逼是 TALK×武力（点名对方手里的东西即讨要）、劝 / 说和 / 赔罪是言辞化解、服 / 敷 / 吃 + 点名之物是 USE（先于调息）、开口要他人之物是言辞讨要、引号里的话不算动作、借势的靠山不是说话的对象、人与物取最先点名者；调息疗伤先于修习判定，但句中有在场之人与出手动词时是出手——「趁龚光杰调息偷袭他」；沉思的关键词（想想 / 寻思 / 沉思 / 盘算 / 回想 / 思索）只在别的动作都没命中时判 THINK（「回想龚光杰那一剑」不是找他说话，「寻思片刻，南下而去」是移动）；MOVE 的此行所为按结构切分——用出口名（出路名或去处名）定位去处、取其后到句末的一段（「去大理城找段正淳」→「找段正淳」），去处后紧跟「的 / 之」的那一处只是修饰（看下一处）、开头的标点连词与趋向补语剥掉、不足两字不算；点了出路且「去」在一切别的动作（取物、出手、修习、赠予、调息、服药、打探、威逼、化解）之前即是动身——后面那件事是此行所为（「去大理城取玉璧」不是在此地取物，「服下金创药，再去剑湖宫」先做的事先算）；找移动动词前先等长遮掉「去 / 往 / 赶」的非移动义（过去的事、失去、望去、往事、以往、赶紧），「想想过去的事」「回想往事」是沉思而不是挪步；去处不在出路里的移动照抄原话交给规则驳回、不带此行所为；点名不在场景里的东西照抄原话交给规则驳回；探索迷雾：scene_names 只收玩家叫得出的名字（认得的出路才算，未知去处的名字与标签一概不收——守卫与 options.compose null；示例里的移动一律写把手（北 / 南 / 东 / 外部），另有往未知区域走与问路各一条；离线解析认方位——先等长遮掉此景一切名字（人、物、功、人群、此地、出路的标签与去处名：「南海鳄神」不是往南），「往」+ 四方四隅即挪步、「向 / 朝」与上下内外须跟着挪步的字（走 / 去 / 奔去 / 爬……），「北上」「南下」「东行」「西去」照认；这个方位上恰有一条出路即落到它的把手，两条或一条也没有就照写方位交给规则驳回（多义不猜），其后到句末是此行所为，点了出路名字的照旧优先；问路先于一切判定（问话常在引号里，故看原话）：问点了名的人，没点名就问不敌视你的在场者里人情最好的一位（平手取快照次序，与菜单的问路同一人），四下无人可问就不是问路，问路恒是寻常手段；大模型把打听此地或去处读成言辞·打探时，由 rules.normalized 规整回问路

依赖说明
- 本层的 LLMClient 抽象也被 infrastructure 的播种管道与厂商客户端引用：外层依赖内层，方向正确
- 地下城主只产出推演（ResolutionOutput；规则与气运产出 Proposal）：定案永远是领域的 resolution.settle → stakes.settle_any，推不出区间内结局的推演整份作废、属性与时钟逐项钳位；它在命令侧玩家锁里同步调用，只为自由文本回合发言（胜负未定或挂着时钟）；点选回合由 FortuneResolver 确定性地取值，不花钱，也不比确定性裁决更凶险，好过确定性裁决的那一格同样欠代价
- 一回合至多五次大模型调用：意图 + 地下城主 + 撞见 / 狭路相逢的判官（≤1）+ 议程（≤1，只在规划时机：初临江湖 / 新的一日 / 江湖震动，一日至多一轮）+ 叙事（含菜单，同一次调用交 <menu>）；寻常回合仍至多三次，H-Agent 只在相撞与规划时机另添；点选回合不调意图与地下城主，结果已定的文本回合只有意图与叙事（眼前挂着时钟时加地下城主一次，只许动时钟、事实、名望）；地下城主与判官不合契约各可重采样一次（attempts=2，仍在 LLM_RESOLUTION_BUDGET 之内）
- 选项是 (玩家状态, 快照) 的纯函数：点选时重算即可核验，不需要任何会话缓存，多进程部署天然一致；焦点与恩怨都由事件折叠进 PlayerState，不另存；导航同理（affordances ∪ navigation 是点选核验的那张表）；最近菜单（RecentMenus）只是体验的缓存（quiet 续接保住风味、点选取回玩家看见的那句），核验不依赖它
- 意图风味封装：菜单先于叙事算出三份——可供性目录（catalogue，编号 m1… 进 <affordances>）、退路菜单（generate）、方位导航（navigation）；说书人在叙事的同一次调用里交 <menu> 挑 3~4 招配武侠风味，options.compose 过闸（key 在目录里、文案合格才换上 flavor_text，否则朴素标签，不足由退路菜单补，一招都没挑中或不交菜单即原样下发退路）；挑什么都落在目录里、执行的永远是那一招的 underlying_command，选项的指令与意图从不进提示词，叙事挑不出新招
- 出路只有一种写法：narrator.way「方位｜去处｜交通方式｜路程」，说书人与地下城主共用，路程取 navigation.duration_label（与导航按钮同一种说法），未知去处写「未知区域」，出口标签（常带地名）不进任何提示词
- 世界心跳的此地之物（时辰、人群约数、此地的事、痕迹还剩多久）只有一种写法：narrator 的 when / cast / headcount / lingering / activity / trace / crowd / chronological，briefs/scene 借用——说书人与地下城主看到的此地之物不会各执一词
